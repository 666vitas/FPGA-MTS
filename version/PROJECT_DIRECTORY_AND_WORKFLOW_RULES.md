# Project Directory and Workflow Rules

## 1. Project Directory Boundary

`E:\new\fpga_lock` is the total project archive and reference repository. It can contain background materials, experiment data, older copies, and non-current development material.

`E:\new\fpga_lock\v94` is the current local project root and the local root corresponding to the GitHub project `666vitas/FPGA-MTS`.

Only the following directories are active development directories for the current project:

- `E:\new\fpga_lock\v94\v0.94`
- `E:\new\fpga_lock\v94\version`
- `E:\new\fpga_lock\v94\software`

Current directory meanings:

1. `E:\new\fpga_lock` is the total project archive.
2. `E:\new\fpga_lock\v94` is the current GitHub/project root.
3. `v0.94` is the FPGA RTL / Vivado / Red Pitaya code development mainline.
4. `version` is the version record, rules, SOP, roadmap, and experiment record mainline.
5. `software` is the upper-computer software development mainline.

## 2. Directories That Are Not Current Mainline

The following directories must not be treated as the current development root or current code mainline:

- `E:\new\fpga_lock`
- `E:\new\fpga_lock\exp_data`
- `E:\new\fpga_lock\文献阅读`
- `E:\new\fpga_lock\vivado_exp`
- `E:\new\fpga_lock\python_sim`
- `E:\new\fpga_lock\open source`

These directories may be used only as reference material, experiment data, or background sources when the user explicitly asks for that context.

## 3. weifang Directory Ban

The current mainline does not use any weifang-related directory.

Strictly prohibited by default:

- Reading `weifang`
- Reading `v-weifang`
- Reading `version-weifang`
- Synchronizing weifang-related directories
- Copying from weifang-related directories
- Modifying weifang-related directories
- Citing weifang-related directories as the current mainline basis

If search results contain `weifang`, `v-weifang`, or `version-weifang`, ignore those results unless the user explicitly says that the task is a historical comparison.

## 4. Agent Roles

### GPT

GPT is responsible for:

1. Reading the GitHub project and newly generated project files.
2. Understanding the current experiment progress.
3. Generating Codex instructions from the user's experiment goals.
4. Helping judge the next experiment wiring, normal observations, and stop conditions.
5. Not directly replacing Codex for local code modification.

### Codex

Codex is responsible for:

1. Reading files in the local `E:\new\fpga_lock\v94` project.
2. Modifying Markdown / RTL / Python according to GPT instructions and user scope.
3. Generating experiment SOPs, code, simulations, and reports.
4. Strictly reporting which files were modified.
5. Not running Vivado by default.
6. Not generating bitstreams by default.
7. Not programming Red Pitaya by default.

### Claude Code

Claude Code is responsible for:

1. Reviewing code generated by Codex.
2. Reviewing RTL for timing risks.
3. Reviewing SOPs for experiment safety risks.
4. Checking whether OUT2 is mistakenly connected to a real actuator.
5. Not acting as the only experiment authority; final validation still requires the user's manual Vivado and oscilloscope checks.

### User

The user is responsible for:

1. Manually opening Vivado.
2. Manually running synthesis and implementation.
3. Manually generating bitstreams.
4. Manually programming Red Pitaya.
5. Manually wiring hardware.
6. Saving oscilloscope screenshots, CSV data, and Vivado timing reports.
7. Reporting experiment observations back to GPT / Codex.

## 5. Default Permission Boundary

By default, Codex must not:

- Run Vivado
- Run synthesis
- Run implementation
- Generate bitstream
- Generate bin
- Program Red Pitaya
- Modify `redpitaya.xpr`
- Modify XDC / SDC
- Touch `weifang`, `v-weifang`, or `version-weifang`

The scope may be expanded only after the user explicitly requests and confirms it.
